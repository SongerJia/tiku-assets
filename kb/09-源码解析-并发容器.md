## 一、为什么需要并发容器

### 1.1 同步容器的困境：一把大锁锁住所有操作

> **说明**：Java 5 之前的并发集合只有"同步包装"——`Hashtable`、`Vector`、`Collections.synchronizedMap` 等。它们的实现是**所有方法都加 synchronized**（整个容器一把锁）：

```java
// Hashtable（JDK 8）：所有读写方法都是 public synchronized
public synchronized V put(K key, V value) { ... }     // 全表锁
public synchronized V get(Object key) { ... }         // 读也要锁！
```

> **说明（为什么慢）**：① **读也要锁**——读多写少场景，读全在抢同一把锁（Hashtable 单线程 put 10 万实测与 CHM 持平，但**多线程读并发度是 1**）；② **串行化**——任何时刻只有一个线程能碰容器；③ **复合操作**（put-if-absent 等）还需要调用方自己再锁。**结论：同步容器 = 正确但并发度恒为 1**。

### 1.2 并发容器家族：四个方向解决四类问题

> **说明**：JUC 并发容器按"解决的问题"分四族（JDK 8）：

| 家族 | 代表 | 解决什么 | 核心手段 |
|---|---|---|---|
| **并发 Map** | `ConcurrentHashMap` | 高并发读写 Map | 分段/桶级锁 + CAS（见第二章） |
| **写复制** | `CopyOnWriteArrayList` / `CopyOnWriteArraySet` | 读多写极少 | 写时复制数组（见第三章） |
| **阻塞队列** | `ArrayBlockingQueue` / `LinkedBlockingQueue` / `SynchronousQueue` / `PriorityBlockingQueue` | 生产者-消费者 | 锁 + 双 Condition 阻塞唤醒（见第四章） |
| **并发辅助** | `ConcurrentLinkedQueue` / `ConcurrentSkipListMap` | 无锁队列 / 有序并发 Map | CAS 无锁 / 跳表 |

> **结论**：**选型第一步 = 判断场景**——读写都要高并发 → CHM；读多写极少 → COW；生产者-消费者解耦 → BlockingQueue；需要有序并发 → ConcurrentSkipListMap。没有"万能并发容器"，只有"匹配场景的容器"。

## 二、ConcurrentHashMap 原理

### 2.1 演进：从 JDK7 分段锁到 JDK8 CAS + 桶锁

> **说明**：CHM 两代架构对比（面试必问）：

| 维度 | JDK 7 | JDK 8（当前） |
|---|---|---|
| 数据结构 | **Segment[] 分段**，每段是一个小 Hashtable | **Node[] 数组**，每个桶（bin）独立 |
| 锁粒度 | 段级锁（默认 16 段） | **桶头节点级锁**（synchronized 锁链表头） |
| 无锁快路径 | 无（都要进段锁） | **空桶 CAS 插入**（完全无锁） |
| 读路径 | 进段锁 | **无锁**（volatile 读 + 链表/红黑树遍历） |
| 并发度 | 固定 16（段数） | **理论桶数**（默认 16，扩容后更高） |
| size() | 每段 count 累加 | baseCount + CounterCell[]（LongAdder 思想） |

> **注意（JDK 8 的锁是怎么用的）**：JDK 8 **没有完全抛弃锁**——桶内冲突时 `synchronized` 锁**桶头节点**（不是整个表），且只在"该桶有冲突"时才锁；**空桶直接 CAS 插入，一次锁都不用**。**"CAS 处理无冲突、锁处理冲突"是 CHM 高并发的核心思想**。

### 2.2 putVal 流程：空桶 CAS 快路径 + 桶锁慢路径

> **说明**：`put` 的完整流程（JDK 8 `putVal`），本机实测验证（`CHMProbe`，8 线程各 put 1000）：

```java
// ConcurrentHashMap.putVal（JDK 8，核心流程语义）：
final V putVal(K key, V value, boolean onlyIfAbsent) {
    // ... hash 计算与校验（null 值禁止）
    for (Node<K,V>[] tab = table;;) {
        Node<K,V> f; int n, i, fh;
        if (tab == null || (n = tab.length) == 0)
            tab = initTable();                        // ① 懒初始化（CAS sizeCtl 抢建）
        else if ((f = tabAt(tab, i = (n - 1) & hash)) == null) {
            // ② 空桶：CAS 直接插入（无锁快路径！）
            if (casTabAt(tab, i, null, new Node<K,V>(hash, key, value)))
                break;
        }
        else if ((fh = f.hash) == MOVED)
            tab = helpTransfer(tab, f);               // ③ 桶是 ForwardingNode → 协助扩容
        else {
            // ④ 桶非空：synchronized 锁桶头节点，再插入/树化
            synchronized (f) {
                // 链表尾插 or 红黑树 putTreeVal（binCount 到 8 转树）
            }
        }
    }
    addCount(1L, binCount);                           // ⑤ 计数（见 2.4）
}
```

```mermaid
flowchart TD
    A[put(key, value)] --> B{数组未初始化?}
    B -->|是| C[initTable 初始化]
    B -->|否| D{目标桶为空?}
    D -->|"是（无冲突）"| E[CAS 直接插入<br/>完全无锁]
    D -->|"否（有冲突）"| F{synchronized 锁桶头<br/>链表尾插 / 转红黑树}
    E --> G[addCount 计数]
    F --> G
    G --> H[超过阈值 → 扩容 transfer<br/>多线程协助]
```

> **结论**：**put 的 80% 场景落在"空桶 CAS"（无锁）或"桶锁"（只锁一个桶）**——并发度从 Hashtable 的 1 提升到桶数级别。本机实测 8 线程各 put 1000，size 精确 8000（无丢失）。

### 2.3 桶内冲突：链表转红黑树的阈值 8/6

> **说明**：JDK 8 桶内结构与 HashMap 相同——**链表 + 红黑树**（hash 冲突严重时）：

| 阈值 | 行为 | 依据 |
|---|---|---|
| binCount **≥ 8** | 链表转红黑树 | 泊松分布：随机 hash 下桶内 ≥8 个节点的概率约 **千万分之六**（0.00000006）——树化是"防御性"的，正常负载下几乎不触发 |
| 树节点 **≤ 6** | 红黑树转回链表 | 避免树/链表在阈值附近来回震荡（8/6 之间留 2 的缓冲） |
| 数组长度 **< 64** | 不树化，先扩容 | 树化前提：数组太小说明 hash 分布差，扩容更划算 |

> **注意（面试高频）**："为什么是 8？"——**8 是泊松分布算出来的防御阈值**：JDK 8 的 HashMap/CHM 注释里给出，桶内节点数 k 的概率 P(k) 在负载因子 0.75 下，k=8 约 6e-8。**它的含义是"正常数据分布下根本到不了 8，到了 8 说明 hash 函数出了妖"**——树化是兜底不是常态。

### 2.4 size() 为什么是"近似值"：baseCount + CounterCell

> **说明**：CHM 的计数复用 LongAdder 思想（见 `09-源码解析-CAS与原子类.md` 3.4）——**`baseCount` 低竞争快路径 + `CounterCell[]` 高竞争分段**：

```java
// ConcurrentHashMap（JDK 8）：
private transient volatile long baseCount;             // 快路径计数
private transient volatile CounterCell[] counterCells; // 高竞争分段计数（@Contended 防伪共享）
// addCount：先 CAS baseCount+1；失败 → 落 CounterCell 分段累加
// size()：
public int size() {
    long n = sumCount();     // baseCount + 所有 CounterCell 累加
    return (n < 0L) ? 0 : (n > Integer.MAX_VALUE) ? Integer.MAX_VALUE : (int) n;
}
```

> **注意（反直觉）**：**CHM 的 size() 不是强一致快照**——sumCount 是"当前时刻的近似汇总"，并发写入时可能略小于真实值。**它不保证精确，只保证不崩溃、近似可用**。业务如果必须精确计数，要么用 `mappingCount()`（long）+ 外部同步，要么自己加锁维护。本机实测 8 线程各 put 1000 后 size=8000（无并发写入时读取，精确）。

## 三、CopyOnWriteArrayList

### 3.1 写复制原理：读无锁，写全量复制

> **说明**：CopyOnWriteArrayList（COW）的设计极端简单：**读操作读一个 `volatile Object[] array`（无锁）；写操作（add/set/remove）先复制整个数组、改副本、再把 array 引用指过去（volatile 发布）**：

```java
// CopyOnWriteArrayList（JDK 8，add 核心）：
private transient volatile Object[] array;    // volatile 数组引用（读方无锁可见）
final ReentrantLock lock = new ReentrantLock();  // 写锁（只保护写）

public boolean add(E e) {
    final ReentrantLock lock = this.lock;
    lock.lock();                                  // 写操作串行（加锁）
    try {
        Object[] elements = getArray();
        int len = elements.length;
        Object[] newElements = Arrays.copyOf(elements, len + 1);  // ★ 全量复制
        newElements[len] = e;
        setArray(newElements);                    // volatile 发布新数组
        return true;
    } finally {
        lock.unlock();
    }
}
// 读：public E get(int index) { return get(getArray())[index]; }  ← 无锁！
```

> **说明（迭代器为什么永不抛 CME）**：迭代器持有的是**创建瞬间的数组快照**——之后无论怎么 add/remove，迭代器读的都是旧数组，**结构永远不变，自然不会 fail-fast**。本机实测（CHMProbe 对照）：

```
// 实测输出（Corretto 8.452）：
[CHM] 迭代中修改未抛 CME(fail-safe) size=16000   ← CHM 迭代中 put 不抛
[HashMap] 迭代中修改触发 fail-fast: ConcurrentModificationException  ← HashMap 迭代中 put 抛
// COW 同理：迭代器是快照，永不 CME
```

> **结论**：COW 用"**空间换并发**"：读路径零锁（性能接近 ArrayList），代价是**每次写复制全数组 O(n) + 写锁串行**。**读多写极少（配置表、黑白名单、监听器列表）是它的主场**。

### 3.2 COW 的代价与适用边界：写放大与内存抖动

> **注意（三个坑，写场景慎用）**：

| 代价 | 说明 | 量级 |
|---|---|---|
| **写 O(n) 复制** | 每次 add 复制整个数组 | 10 万元素 add 一次 = 复制 10 万引用 |
| **内存瞬时翻倍** | 旧数组 + 新数组同时存在 | 大数组频繁写 → 内存峰值翻倍 + GC 压力 |
| **数据弱一致** | 读可能看不到刚写的值（看到旧快照） | 迭代器/并发读的"旧视图"是特性不是 bug |

```java
// 场景判断：写频率高（>每秒几十次）且数组大 → 别用 COW
CopyOnWriteArrayList<String> config = new CopyOnWriteArrayList<>();  // ✅ 配置表：读极多写极少
CopyOnWriteArrayList<String> hot = new CopyOnWriteArrayList<>();     // ❌ 高频写入的日志/消息列表 → 内存抖动 + GC 卡顿
```

> **结论（选型）**：COW 一句话——**"读比写多 100 倍以上、数组不太大"才划算**。写多或数组大，退回 `synchronizedList`（写快读锁）或 BlockingQueue（解耦）。

## 四、BlockingQueue 家族

### 4.1 阻塞队列全景：五兄弟与四个操作姿势

> **说明**：`BlockingQueue` 接口定义四个操作姿势（JDK 8），分别对应"不等待/等待/超时/抛异常"：

| 操作 | 抛异常 | 返回特殊值 | 阻塞等待 | 超时等待 |
|---|---|---|---|---|
| **入队** | `add(e)` | `offer(e)`（满返回 false） | `put(e)`（满则阻塞） | `offer(e, time, unit)` |
| **出队** | `remove()` | `poll()`（空返回 null） | `take()`（空则阻塞） | `poll(time, unit)` |

| 队列 | 有界? | 锁 | 特点 |
|---|---|---|---|
| **ArrayBlockingQueue** | ✅ 有界 | 1 把锁 + 2 Condition | 数组，容量固定，最常用 |
| **LinkedBlockingQueue** | 可选（默认无界） | **2 把锁**（take/put 分离） | 链表，默认容量 Integer.MAX_VALUE（无界坑） |
| **SynchronousQueue** | 无容量 | 无（CAS） | 交接模式：put 必须等 take，不缓存任务 |
| **PriorityBlockingQueue** | 无界 | 1 把锁 | 优先级出队 |
| **DelayQueue** | 无界 | 1 把锁 | 延迟到期才可出队（定时任务用） |

> **结论**：选型口诀——**固定容量缓冲用 ArrayBlockingQueue；高吞吐无界流用 LinkedBlockingQueue（注意 OOM）；线程池交接用 SynchronousQueue（CachedThreadPool 就是它）；定时调度用 DelayQueue/ScheduledThreadPoolExecutor**。

### 4.2 ArrayBlockingQueue：一把锁 + 双 Condition 的分工唤醒

> **说明**：`ArrayBlockingQueue` 是 AQS Condition 的经典应用（呼应 `09-源码解析-AQS与ReentrantLock.md` 第六章）：**一把 ReentrantLock + `notEmpty`/`notFull` 两个 Condition**——生产者 put 阻塞在 notFull（等空位），消费者 take 阻塞在 notEmpty（等元素），**各唤醒各的，不惊群**：

```java
// ArrayBlockingQueue（JDK 8，核心字段与 put/take）：
final ReentrantLock lock;                    // 唯一锁
private final Condition notEmpty;            // 消费者等"有货"
private final Condition notFull;             // 生产者等"有空位"

public void put(E e) throws InterruptedException {
    lock.lockInterruptibly();
    try {
        while (count == items.length)        // 满了 → 等空位
            notFull.await();                 // 挂到 notFull 条件队列
        enqueue(e);                          // 入队
        notEmpty.signal();                   // 通知一个消费者"有货了"
    } finally { lock.unlock(); }
}
public E take() throws InterruptedException {
    lock.lockInterruptibly();
    try {
        while (count == 0)                   // 空了 → 等货
            notEmpty.await();
        E x = dequeue();                     // 出队
        notFull.signal();                    // 通知一个生产者"有空位了"
        return x;
    } finally { lock.unlock(); }
}
```

> **注意（为什么 while 不是 if）**：条件等待一律用 `while (count == items.length)` 循环判断——**防止"假唤醒"（spurious wakeup）**：线程被唤醒后条件可能又变了（被别的线程抢了空位），必须重新检查。**这是所有条件等待的规范写法**（Object.wait 同理）。

**完整可运行 demo（生产者-消费者，容量 2）**：

```java
// BlockingQueueDemo.java —— 容量 2 的 ArrayBlockingQueue，1 生产者 + 2 消费者
import java.util.concurrent.*;

public class BlockingQueueDemo {
    public static void main(String[] args) throws Exception {
        BlockingQueue<Integer> q = new ArrayBlockingQueue<>(2);   // 有界：满则 put 阻塞
        // 生产者：每 200ms 产一个，共产 6 个（put 满时阻塞等空位）
        Thread producer = new Thread(() -> {
            try { for (int i = 1; i <= 6; i++) { q.put(i); System.out.println("put " + i); } }
            catch (InterruptedException ignored) {}
        }, "producer");
        // 消费者：take 空时阻塞等货
        Thread c1 = new Thread(() -> { try { for (int i = 0; i < 3; i++)
            System.out.println("c1 take " + q.take()); } catch (InterruptedException ignored) {} }, "c1");
        Thread c2 = new Thread(() -> { try { for (int i = 0; i < 3; i++)
            System.out.println("c2 take " + q.take()); } catch (InterruptedException ignored) {} }, "c2");
        producer.start(); c1.start(); c2.start();
        producer.join(); c1.join(); c2.join();
        // 观察点：容量 2 的队列，put 到第 3 个时生产者必然阻塞，直到消费者 take 腾出空位
    }
}
```

> **说明**：运行观察——生产者 put 到第 3 个时被阻塞（队列满），消费者 take 一个后生产者才继续；**put 阻塞 → notFull.await，take 后 → notFull.signal**——完整闭环就是 4.2 的双 Condition 协作。

### 4.3 LinkedBlockingQueue：两把锁为什么更快

> **说明**：`LinkedBlockingQueue` 的优化是**take/put 各一把锁**（JDK 8）：入队只碰 `putLock` + `last` 节点，出队只碰 `takeLock` + `head` 节点——**生产者和消费者可以同时干活**，互不阻塞：

```java
// LinkedBlockingQueue（JDK 8，双锁结构）：
private final ReentrantLock takeLock = new ReentrantLock();   // 出队锁
private final Condition notEmpty = takeLock.newCondition();
private final ReentrantLock putLock = new ReentrantLock();    // 入队锁
private final Condition notFull = putLock.newCondition();
private final AtomicInteger count = new AtomicInteger();      // 计数器（CAS，见 CAS 篇）
// put：putLock.lock() → 尾插 → count.getAndIncrement() → signalNotEmpty
// take：takeLock.lock() → 头出 → count.getAndDecrement() → signalNotFull
```

> **注意（为什么 ArrayBlockingQueue 没用双锁）**：数组的 put/take 操作**共享同一块环形缓冲区**（`items` + `putIndex`/`takeIndex`），读写索引互相纠缠，双锁反而引入更多复杂性；链表 put 摸尾、take 摸头，天然可分离。**"锁的粒度由数据结构的耦合度决定"**——这就是 ABQ 一把锁、LBQ 两把锁的源码层理由。

## 五、并发容器选型与踩坑

### 5.1 选型对照表：场景 → 容器

> **说明**：把全部并发容器按场景归位（决策表）：

| 场景 | 推荐 | 理由 |
|---|---|---|
| 高并发读写 Map | **ConcurrentHashMap** | 桶级锁 + 空桶 CAS |
| 读多写极少（配置/白名单） | **CopyOnWriteArrayList/Set** | 读无锁 |
| 生产者-消费者解耦 | **ArrayBlockingQueue / LinkedBlockingQueue** | 阻塞 + 双 Condition |
| 线程池任务交接 | **SynchronousQueue** | 零缓存交接（CachedThreadPool） |
| 有序并发遍历 | **ConcurrentSkipListMap** | 跳表无锁读 |
| 无锁高吞吐队列 | **ConcurrentLinkedQueue** | CAS 入队/出队 |
| 需要精确 size/强一致 | 同步容器 + 外部锁 | CHM size 是近似值 |

> **结论**：**选型的本质是"一致性要求 × 读写比例 × 容量边界"三维决策**——要强一致就别贪并发（上锁），要并发就得接受弱一致（CHM/COW 的近似语义）。

**有序并发 Map 与无锁队列的用法（补充两个小众容器）**：

```java
// ConcurrentSkipListMap：有序 + 并发（跳表实现，读无锁、范围查询友好）
ConcurrentSkipListMap<Integer, String> skiplist = new ConcurrentSkipListMap<>();
skiplist.put(3, "c"); skiplist.put(1, "a"); skiplist.put(2, "b");
System.out.println(skiplist.firstKey());          // 1 —— 天然有序（TreeMap 的并发版）
System.out.println(skiplist.subMap(1, 3));        // {1=a, 2=b} —— 范围查询
// 适用：排行榜/区间查询/有序快照，代价是常数因子比 CHM 高（跳表多级索引）

// ConcurrentLinkedQueue：CAS 无锁队列（无界，无阻塞，生产者-消费者需自旋取）
ConcurrentLinkedQueue<String> clq = new ConcurrentLinkedQueue<>();
clq.offer("t1"); clq.offer("t2");
String task = clq.poll();                          // 无锁弹出（空返回 null，不阻塞）
// 适用：无界高频入队 + 轮询消费；需要阻塞等待用 BlockingQueue
```

### 5.2 真实踩坑：size 不精确、迭代器弱一致、无界队列

> **注意（三个生产事故点）**：

```java
// 坑1：CHM.size() 是近似值 —— 依赖精确计数的业务（如"还剩多少库存"）别直接用它
if (map.size() == 0) { /* 可能误判：并发写时 size 读到旧值 */ }
// 正确：需要强一致的场景用锁 + 独立计数器，或用 AtomicLong 自己维护

// 坑2：CHM/COW 迭代器是弱一致 —— "迭代时修改"不抛 CME，但迭代器看不到新增
for (K k : map.keySet()) { /* 并发 put 的新键不一定在本次迭代里出现 */ }
// 弱一致是"不抛异常"的代价：要强一致快照就复制一份再迭代

// 坑3：无界队列 = 内存敞口 —— LinkedBlockingQueue() 默认容量 Integer.MAX_VALUE
new LinkedBlockingQueue<>();        // 生产者快于消费者 → 任务堆积到 OOM
new LinkedBlockingQueue<>(1000);    // 必须给容量！配合拒绝策略
```

> **结论（工程纪律）**：**① 精确性要求上锁、不要指望近似 API；② 弱一致不是 bug 是特性，用之前先确认语义；③ 队列一律有界**。并发容器的每个"快"都对应一个"弱"，选型时先问"我能接受哪种弱"。

> **收尾一句话**：并发容器的机器层 = "CAS 处理无冲突 + 细粒度锁处理冲突 + 分段/复制/双锁分摊竞争"；它把并发从"全表一把锁"进化到"哪里冲突锁哪里"——CHM 的桶锁、COW 的复制、LBQ 的双锁，是同一思想的三种落地。

## 收尾：核心概念对照表 + 关键设计思想 + 面试 Q&A

### 核心概念对照表

| 概念 | 一句话 | 关键数字/证据 |
|---|---|---|
| Hashtable | 全表 synchronized，并发度 1 | 单锁 |
| CHM JDK7 | Segment 分段锁（16 段） | 并发度 16 |
| CHM JDK8 | CAS + 桶头锁 + 红黑树 | 空桶无锁；实测 8000 无丢失 |
| 树化阈值 | 桶内 ≥8 转红黑树 | 泊松分布 ~6e-8 |
| size() | baseCount + CounterCell 近似值 | 非强一致 |
| COW | 写全量复制，读无锁 | 写 O(n)，读 O(1) |
| ABQ | 1 锁 + notEmpty/notFull | while 防假唤醒 |
| LBQ | take/put 双锁 + AtomicInteger | 生产者消费者并行 |

### 关键设计思想（编号列表）

1. **锁粒度决定并发度**：从全表锁 → 段锁 → 桶锁 → 无锁 CAS，粒度越细并发越高，复杂度也越高。
2. **无冲突 CAS、有冲突锁**：CHM 把"绝大多数 put 落在空桶"的统计规律变成性能——多数操作零锁。
3. **空间换并发**：COW 的复制、CHM 的 CounterCell、LBQ 的双锁，都是"多点内存换多点并行"。
4. **弱一致是特性**：近似 size、快照迭代器、非强一致——每个都对应一次性能换取，用前先确认语义。
5. **条件等待用 while**：假唤醒是并发编程的现实，循环重查条件是唯一安全的写法。

### 面试题 Q&A

**Q1：ConcurrentHashMap JDK7 和 JDK8 有什么区别？**
> JDK7：Segment[] 分段锁（默认 16 段），每段是一个小 Hashtable，put 先定位段再进段锁，并发度固定 16。JDK8：弃分段，Node[] + 空桶 CAS 无锁插入 + 非空桶 synchronized 锁桶头节点，桶内链表 ≥8 转红黑树；并发度提升到桶级；size() 用 baseCount + CounterCell（LongAdder 思想）。JDK8 的读全程无锁（volatile 读）。

**Q2：CHM 的 put 流程是怎样的？为什么快？**
> putVal：① 数组未初始化 → CAS 抢建（sizeCtl）；② 目标桶空 → CAS 直接插入（无锁快路径，80% 场景）；③ 桶是 ForwardingNode（扩容中）→ 协助扩容；④ 桶非空 → synchronized 锁桶头，链表尾插或树化；⑤ addCount 计数。快的原因：多数 put 落在空桶 CAS（无锁），有冲突也只锁一个桶，并发度 = 桶数级别。实测 8 线程各 put 1000，size 精确 8000。

**Q3：CopyOnWriteArrayList 的原理和代价？**
> 原理：volatile Object[] 数组引用 + 写锁。读直接读数组（无锁）；写（add/remove）先复制整个数组改副本，再 volatile 发布新引用。迭代器持有快照，永不抛 CME。代价：写 O(n) 全量复制、内存瞬时翻倍（旧+新数组共存）、数据弱一致（读可能看到旧快照）。适用：读多写极少（配置表/白名单）；高频写场景会内存抖动 + GC 压力。

**Q4：ArrayBlockingQueue 和 LinkedBlockingQueue 的区别？**
> ABQ：有界数组，一把锁 + notEmpty/notFull 双 Condition，put 满阻塞、take 空阻塞，双 Condition 分工唤醒（生产者只唤醒消费者）。LBQ：链表（默认无界），take/put 两把锁 + AtomicInteger 计数，生产者和消费者可并行操作（一个摸头一个摸尾）。ABQ 用一把锁是因为数组的 put/take 索引共享同一缓冲区、耦合度高；LBQ 头尾分离天然可双锁。生产上用 ABQ 有界 + 双 Condition 最稳。
